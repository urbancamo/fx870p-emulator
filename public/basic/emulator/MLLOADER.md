# ML Loader

A generic machine-language loader for the FX-870P/VX-4. Receives a compiled `.hex` file over COM0 serial, POKEs the decoded bytes into Bank 1 RAM at `&H1CD0`, verifies a checksum, then executes via `MODE110`.

Companion to the BASIC compiler at `tools/compiler/`. Load this program once — it works for any compiled program.

**Requires `EXTCLR.BAS` to have been run first** — see "Why EXTCLR.BAS is required" below.

## Usage

1. Run `EXTCLR.BAS` once (see `EXTCLR.md`) — reserves the `&H1CD0` area against BASIC's own memory use
2. Open the library (**LIB**), load `MLLOADER.BAS` into P0
3. Type `RUN` and press `[EXE]`
4. LCD shows `ML loader - send .hex now` / `Beep x1 = done, x3 = err.`
5. In the COM0 panel, click **LOAD** and pick a `.hex` file generated by the compiler
6. On success: one **BEEP**, then the compiled program runs automatically via `MODE110`
7. On failure (checksum mismatch): three **BEEP**s and the loader ends, returning to the `Ready` prompt
8. If step 1 was skipped or reserved too little space: `No ML area! / Run EXTCLR first.` and the loader ends cleanly, before touching any payload bytes

No progress text is printed during the transfer itself — see "Why no PRINT or string variable during receive" below for why.

## Protocol

The `.hex` file is ASCII text, CR-delimited, one field per line (safe for any serial link — no binary escape hazards, and lets Casio BASIC read a fixed-width field at a time):

```
[line]  4 hex chars: 16-bit payload size, big-endian
[line]  size × (2 hex chars): binary payload, one byte per line
[line]  2 hex chars: 8-bit additive checksum over payload bytes
```

Example: a 3-byte binary `48 65 6C` encodes as `0003\r48\r65\r6C\r19\r`:
- `0003` — size (3 bytes)
- `48`, `65`, `6C` — payload, one byte per line
- `19` — checksum (0x48 + 0x65 + 0x6C = 0x119 → 0x19 mod 256)

Generated by `generateHexPayload()` in `tools/compiler/loader.ts`.

## COM0 Settings

```
OPEN "COM0:6,E,8,1,N,N,N,B,N" FOR INPUT AS #1
```

| Field | Meaning                                |
|-------|----------------------------------------|
| 6     | 4800 baud                              |
| E     | Even parity                            |
| 8     | 8 data bits                            |
| 1     | 1 stop bit                             |
| N,N,N | CS/DS/CD unused                        |
| B     | XON/XOFF flow control (required)       |
| N     | SI/SO code system unused               |

`Busy=B` is **required**: each receive iteration (parsing two hex chars plus the line's CR
terminator) takes long enough that the 64-char UART buffer can fill before BASIC drains it.
Without XON/XOFF back-pressure this produces a `BV error` (buffer overflow) part-way through
the transfer. The Casio BASIC default for `Busy` is `B`, so this just matches the default
explicitly.

## Why EXTCLR.BAS is required

The FX-870P/VX-4 ROM hard-codes the string-operation stack pointer (`US`) to `&H1CD0` — see
`rom1a.src` `&H1F64`, `&H66BA`, and other call sites. This is not just a one-time boot
default: the ROM re-arms `US=&H1CD0` on essentially every string operation, including a
*transient* one whose result is never stored in a variable.

`INPUT$(1,#1)` — the primitive this loader must use to read each byte off COM0 — is itself a
string-returning operation. Even written as `A=ASC(INPUT$(1,#1))`, with the string never
named or persisted, the ROM still writes the returned character through `US` at `&H1CD0` as
part of constructing that return value. Because `US` is a fixed address (it doesn't track the
loop counter `I`), *every* `INPUT$` call across the whole receive loop stomps `&H1CD0` — not
just the one for byte 0. The `POKE I,P` for iteration 0 briefly restores the correct byte
there, but every later iteration's `INPUT$` calls overwrite it again, and nothing pokes it
back a second time. The final state of `&H1CD0` ends up being whatever the very *last*
`INPUT$` call in the whole program read — deterministically, the checksum line's trailing CR
(`&H0D`) — regardless of what was actually POKEd there during the loop. A second, similarly
fixed ROM address (plausibly the UART's own receive-staging buffer) causes one further
byte to be corrupted the same way.

This is unavoidable from BASIC alone: there is no way to read serial data (`INPUT$`, `INPUT#`,
`LINE INPUT#`) without it being string-typed at the ROM level. **`EXTCLR.BAS` fixes this by
moving `US` and the UART buffer below `&H1CD0` entirely** (see `EXTCLR.md`), so their
incidental writes no longer land on the loaded program.

### Why no PRINT or string variable during receive (still true, but no longer sufficient alone)

Two things were tried before `EXTCLR.BAS` was added, and both still apply as good practice,
but neither fully solves the problem on their own:

1. **PRINT after POKE.** All user-facing messages are printed *before* the POKE loop
   (lines 810/815); after loading, success/failure is signalled with `BEEP` only, never `PRINT`.
2. **Avoiding a persisted string variable.** Earlier versions of this loader read each line
   into `A$` (`LINE INPUT #1,A$` / `INPUT #1,A$`), reassigned on every iteration — this caused
   much more severe, cascading corruption than the residual 1-2 byte issue described above.
   The receive loop (lines 900/950) reads one character at a time via `INPUT$(1,#1)` straight
   into numeric variables (`A`, `B`, `P`) and never stores a string in a named variable, which
   is still the right approach — it's just that even an *unnamed* string return isn't enough
   to dodge `US`.

## Safety check

Before starting the POKE loop, the loader checks that the reserved area is big enough:

```basic
805 IOBF=PEEK(&H1895)+PEEK(&H1896)*256
...
832 IF EX+N<IOBF THEN 845
835 CLOSE:PRINT "No ML area!":PRINT "Run EXTCLR first.":END
```

`IOBF` is the current top of BASIC's work area (same address CosmicV4.bas itself checks). If
the payload's end address (`EX+N`) isn't safely below it, the loader bails out with a clear
message instead of silently corrupting memory. This check runs after `OPEN` and after reading
the size field (both required to know `N`), but before any payload byte is read or POKEd, so
it's safe to `PRINT` here.

## Target Address

The loader always POKEs to `&H1CD0` (standard FX-870P/VX-4 ML area, same address used by CosmicV4). The compiled programs are ORG'd to match. To use a different load address, edit line 800 (`DEFSEG=`/`EX=`).

## MODE110 Quirk

The final line uses a variable for the execution address:

```basic
800 DEFSEG=&H01CD:EX=&H1CD0:S=0
...
100 CLS:GOSUB 800:MODE110(EX):END
```

Directly passing a hex literal (`MODE110(&H1CD0)`) produces a SN error — Casio BASIC's MODE command parser requires a variable argument. This matches CosmicV4's convention.
