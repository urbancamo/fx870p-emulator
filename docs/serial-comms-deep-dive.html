1. Answers at a glance

QuestionAnswerEvidence
No hardware flow control? Default: yes — CS/DS/CD all default to N, so out of the box no hardware line gates the data path. But hardware flow control is fully implemented and selectable. Default open string COM0:2,E,8,1,N,N,N,B,N (FX-850P manual, part 9); parser 0x4EBD stores flags that the driver genuinely tests.
Uses the CTS line? Yes, on transmit, when CS=C. Before every byte the ROM busy-waits until CTS is asserted. CTS is also re-checked before the ROM emits an XOFF of its own. 0x8662 reads modem-status reg 0x0006, masks bit 2 (CTS); caller 0x85FB spins at 0x860A. XOFF path re-check at 0x8433.
Uses the RTS line? Not dynamically. RTS (DB-25 pin 4) and DTR (pin 20) are outputs on the connector, but no ROM code was found toggling them per-byte or per-buffer state. They behave as statically asserted "interface powered" signals. Receive-side throttling is done with XOFF, not by dropping RTS. Exhaustive search of the driver block 0x8314–0x86C2 shows writes only to gate-array regs 2/3/4/5/7; no RTS/DTR bit appears in the RX buffer-full path (which sends XOFF instead).
Other RS-232C lines? DSR and DCD, both as receive/send qualifiers. DS=D: transmit waits for DSR, and a byte received while DSR is off is rejected ("Not ready" → NR error). CD=C: a byte received while carrier is off is rejected the same way. Also SI/SO (0x0F/0x0E) code shifting when Code=S with 7 data bits. TX gate 0x8662/0x866F masks CTS+DSR (0x0C); RX ISR 0x83E4–0x83ED masks DSR+DCD (0x18) → "Not ready" at 0x8392. SI/SO at 0x83F4 (RX) and 0x861D (TX).
Honours the RS-232C protocol or its own timing? Genuine RS-232C. Framing (start bit, 7/8 data, optional parity, 1–2 stop bits) and the bit clock are generated by a dedicated gate-array UART; the CPU never bit-bangs. Standard asynchronous start-stop, full duplex. The speed digit is written as a raw 3-bit code to the gate array, which derives the baud clock in hardware. UART regs memory-mapped at bank 3 offsets 0–7; RSOPN 0x84EC programs regs 3/4/5; baud code shifted into reg 0x0004 at 0x8500–0x8507. RX completion raises interrupt INT1.
Delays in sending / receiving? TX: polls the TX-ready status bit before each byte (with a timeout and a double-read debounce) — so the ROM sends back-to-back at full line rate, no artificial inter-character gap. A fixed ≈3 ms delay exists only when (re)programming the UART registers, and a baud-scaled drain delay runs at CLOSE. RX: interrupt-driven — each received byte is buffered from the INT1 ISR with no polling delay. TX-ready wait 0x8678 (timeout 0x0890 loops; consistency check 0x868A–0x8690); 3 ms loop 0x8335; baud-scaled delay 0x86A3; ISR entry 0x83B9 via INT1 vector.
Delays processing BASIC tokens at line end? Yes — and the driver is built for them. Tokenization after each received CR happens at task level while the ISR keeps filling a 256-byte ring buffer. If tokenization is slow, the count climbs; at 192 bytes (75%) the ISR transmits XOFF; when the consumer drains it below 32 bytes an XON goes out. With Busy=N the same stall instead ends in a hard buffer-overflow (BV error). Thresholds at 0x8429 (sbc $3,&HC0) and 0x859B (sbc $1,&H20); overflow latch 0x8424 → RS4=0x01.
XON/XOFF honoured? Which direction? Both directions, when Busy=B (the default). As receiver it sends XOFF/XON on the 192/32-byte thresholds. As transmitter it consumes incoming 0x11/0x13 (they never reach the buffer), latches a suspend flag, and pauses before the next byte until XON arrives. The pause is checked per byte — a byte already started completes. Send: 0x8442–0x8447 (XOFF), 0x85B7–0x85C0 (XON). Honour: ISR 0x840C/0x8411 → RS2 bit1; PRTRS gate 0x8611–0x8614.

2. Hardware architecture — how the CPU reaches the serial port

The FX-870P's serial port is not bit-banged through the HD61700's general-purpose Port D (that port is the Centronics printer interface — strobe on bit 3, busy on bit 5). Instead a dedicated gate-array UART sits in the memory map: physical addresses 0x30000–0x30007 (bank 3, offsets 0–7). The ROM reaches it with the standard bank-switch idiom — pst ua,&HF4 to point IX/IZ at bank 3, ordinary ld/st to the low offsets, then pst ua,&H54 to restore bank 1 (RAM).

Key consequences:

  • Framing, bit timing and parity generation/checking are done in hardware. The CPU's only timing duties are polling TX-ready and servicing INT1.
  • The modem-status inputs CTS/DSR/DCD are readable by software at register 0x0006 (bits 2/3/4) — this is what makes real hardware handshaking possible even though the emulators don't model those lines.
  • Receive is fully interrupt-driven: RX-complete raises INT1, vectored via ROM0 0x0032 → jp &H0D77 → dispatch 0D83: jp &H83B9.

3. The OPEN "COM0:" string and its parser

Syntax (FX-850P owner's manual, part 9): COM0:Speed,Parity,Data,Stop,CS,DS,CD,Busy,Code — default COM0:2,E,8,1,N,N,N,B,N.

#FieldValuesDefaultStored as

2ParityN / E / OERS1 bits 1–2
3Data bits7 / 88RS1 bit 3
4Stop bits1 / 21RS1 bit 4
5CS (CTS)C = wait for CTS before sending · N = ignoreNRS3 bit 2
6DS (DSR)D = wait on send, NR error on receive if off · NNRS3 bit 3
7CD (DCD)C = NR error on receive if carrier off · NNRS3 bit 4
8BusyB = XON/XOFF flow control · N = noneBRS3 bit 1
9CodeS = SI/SO shift codes (7-bit data only) · NNRS3 bit 0

The parser lives at 0x4EBD in ROM1 (reached when the device-name matcher recognises COM0: as device type 2 from the table at 0x14A4). It accumulates RS1 in $12 and RS3 in $13. The five letter-flags all use one helper (0x4F4E) taking a set-letter, a clear-letter ('N') and a bit mask:

4F19:  ld   $4,&H4E       ; $4 = 'N' — clear-letter routes result to RS3
4F1C:  ldw  $2,&H43FB     ; CS  : set-letter 'C', mask 0xFB → RS3 bit 2
4F20:  cal  &H4F4E
4F23:  ldw  $2,&H44F7     ; DS  : set-letter 'D', mask 0xF7 → RS3 bit 3
4F27:  cal  &H4F4E
4F2A:  ldw  $2,&H43EF     ; CD  : set-letter 'C', mask 0xEF → RS3 bit 4
4F2E:  cal  &H4F4E
4F31:  ldw  $2,&H42FD     ; Busy: set-letter 'B', mask 0xFD → RS3 bit 1 (XON/XOFF)
4F35:  cal  &H4F4E
4F38:  ldw  $2,&H53FE     ; Code: set-letter 'S', mask 0xFE → RS3 bit 0 (SI/SO)
4F3C:  cal  &H4F4E

At OPEN the results are committed: RS1/RS3 to the descriptor copy at 0x173E/0x173F (84AE: pre ix,&H173E … stw $12,(ix+$sx)) and the live set RS1–RS4 to 0x1554–0x1557 (84B4: pre ix,&H1554 … stm $11,(ix+$sx),4). Then RSOPN (0x84EC) programs the gate array: the baud field is rotated down to bits 0–2 and written to register 0x0004 — there is no ROM baud table; the gate array decodes the 3-bit code itself:

84FD:  ld   $3,$11        ; RS1
8500:  did  $3
8502:  bid  $3            ; baud code now in bits 0–2
8504:  ld   $4,&H08
8507:  cal  &H8328        ; write gate-array regs 0x0004/0x0005 (strobe+latch, ≈3 ms delay)

Transmit gate — annotated listing

The "is the other end ready?" check reads modem-status register 0x0006, inverts the active-low CTS/DSR bits, masks them with the enabled flags from RS3, and returns non-zero if any enabled line is de-asserted:

8662:  pre  iz,&H0002
8666:  ld   $0,(iz+&H04)  ; read modem status reg (0x0006)
8669:  xr   $0,&H0C       ; invert CTS (bit2), DSR (bit3)
866C:  an   $0,$4         ; $4 = RS3 — keep only ENABLED handshakes
866F:  anc  $0,&H0C       ; CTS, DSR   → Z set only when all enabled lines ready

; caller PRTRS (0x85FB): spin until ready, then check software flow control
8604:  ldm  $2,(ix+$sx),3 ; $2=RS1  $3=RS2  $4=RS3
8607:  cal  &H8662        ; other end ready to receive?
860A:  jr   nz,&H85FD     ; *** busy-wait on CTS/DSR ***
860C:  anc  $4,&H02       ; XON/XOFF enabled?
860F:  jr   z,&H8616      ; no → transmit
8611:  anc  $3,&H02       ; RS2 bit1: remote sent XOFF?
8614:  jr   nz,&H85FD     ; *** paused until ISR clears it on XON ***

Receive gate — annotated listing

83E4:  xr   $0,&H1C       ; invert DCD (bit4), DSR (bit3), CTS (bit2)
83E7:  an   $0,$5         ; $5 = RS3 — keep only enabled handshakes
83EA:  anc  $0,&H18       ; DSR + DCD only (CTS is not a receive qualifier)
83ED:  jr   nz,&H8392     ; → "Not ready": RS4 = 0x08, byte discarded → NR error
RTS/DTR: no code in the driver block manipulates an RTS or DTR output bit — in particular the buffer-full path sends XOFF rather than dropping RTS. Treat RTS/DTR as statically asserted "port open" indicators. A PC-side interface must therefore not wait for RTS transitions as flow control; use XON/XOFF (or wire the PC's RTS to the Casio's CTS and open with CS=C to let the PC throttle the Casio).

5. XON/XOFF — sent and honoured

With Busy=B (the default) the ROM implements symmetric software flow control around its 256-byte receive ring buffer. Two independent state bits keep the directions separate: RS3 bit 6 = "we sent XOFF" (protecting our buffer), RS2 bit 1 = "remote sent us XOFF" (pausing our transmitter).

→ transmit XOFF (0x13) Throttled --> Flowing : RSGET drains RXCNT below 32
→ transmit XON (0x11) } state "Transmitter side (RS2 bit1)" as T { [*] --> Sending Sending --> Suspended : XOFF (0x13) received
(consumed by ISR, not buffered) Suspended --> Sending : XON (0x11) received }

Sending XOFF — in the receive ISR, after storing each byte

8420:  ad   $3,$sy        ; RXCNT++
8424:  jp   c,&H839E      ; 256-byte wrap → hard overflow, RS4=0x01 (BV error)
8429:  sbc  $3,&HC0       ; is the buffer 75% full? (192 bytes)
842C:  jr   c,&H844D      ; not yet → done
842E:  anc  $5,&H40       ; XOFF already in progress?
8431:  jr   nz,&H844D     ; yes → don't send twice
8433:  anc  $0,&H0C       ; CTS/DSR still asserted? (don't jam the line)
8436:  jr   nz,&H844D
8438:  ld   $0,(iz+$sy)   ; verify TX-ready (double-read: status may glitch)
8442:  ld   $0,&H13       ; XOFF code
8445:  std  $0,(iz+$sx)   ; (0x0002) ← 0x13 — transmit XOFF
8447:  or   $5,&H40       ; latch "XOFF in progress" (RS3 bit6)

Sending XON — in RSGET, after removing each byte

8597:  sb   (ix+$sx),$30  ; RXCNT--
859B:  sbc  $1,&H20       ; fewer than 32 bytes left?
859E:  rtn  nc            ; still ≥32 → nothing to do
85A2:  anc  $4,&H02       ; XON/XOFF enabled?
85A6:  anc  $4,&H40       ; did WE send XOFF earlier?
85B2:  cal  &H8662        ; wait until remote ready (CTS/DSR)
85B7:  ld   $0,&H11       ; XON code
85BA:  cal  &H865C        ; NTX0: transmit 0x11
85C0:  sb   (ix+$sx),$0   ; clear "XOFF in progress"

Honouring received XON/XOFF — in the ISR, before buffering

8407:  anc  $5,&H02       ; XON/XOFF enabled?
840C:  sbc  $1,&H11       ; XON — resume transmission
840F:  jr   z,&H8472
8411:  sbc  $1,&H13       ; XOFF — suspend transmission
8414:  jr   z,&H846E
   …
846E:  or   $4,&H02, jr &H845E   ; XOFF → set RS2 bit1 (TX suspended)
8472:  an   $4,&HFD, jr &H845E   ; XON  → clear RS2 bit1 (TX resumes)
845E:  st   $4,(ix+$sy)          ; note: 0x11/0x13 are CONSUMED, never buffered

Consequence: with Busy=B the link is not 8-bit-clean — binary payloads containing 0x11/0x13 are swallowed by the ISR. Binary transfers must either hex-encode (as the project's ML loader does) or open with Busy=N and pace the sender.

7. Line-end BASIC tokenization delays

During LOAD "COM0:…" the interpreter reads a line up to CR, then tokenizes and stores it before reading on. Tokenization runs at task level with interrupts enabled, so incoming bytes keep landing in the ring buffer. The 256-byte buffer with the 192-byte XOFF threshold is precisely the mechanism that absorbs these stalls:

sequenceDiagram participant PC as Sender (PC) participant ISR as INT1 ISR 0x83B9 participant BUF as Ring buffer (0x1559 count) participant BAS as BASIC tokenizer PC->>ISR: "100 FOR I=0 TO N-1" + CR ISR->>BUF: store bytes (count rises) BUF->>BAS: RSGET drains line up to CR Note over BAS: tokenize + insert program line
(long lines / renumber → slow) PC->>ISR: next line bytes keep arriving ISR->>BUF: count climbs during tokenization alt count reaches 192 (Busy=B) ISR->>PC: XOFF (0x13) Note over PC: sender pauses BAS->>BUF: tokenization done, RSGET drains BUF-->>ISR: count drops below 32 ISR->>PC: XON (0x11) via RSGET Note over PC: sender resumes else Busy=N and count wraps 256 ISR->>BUF: RS4 = 0x01 (overflow) Note over BAS: LOAD aborts with BV error end

Headroom arithmetic: from an empty buffer the sender can stream 192 bytes before XOFF is triggered — at 4800 baud (≈2.3 ms/char with parity) that is ≈440 ms of continuous tokenization the Casio can hide without ever throttling; at 300 baud ≈7 s. This is why short BASIC lines load reliably even without flow control, while long dense lines at 4800 baud with Busy=N are exactly the case that produces BV errors. (The project's own MLLOADER hit this failure mode: its per-byte INPUT #1 parsing was slow enough to overrun without XON/XOFF.)

9. Corrections to earlier annotations & emulator gaps

Corrections to reference/fx870p-rom-annotations.md: the label "COM0_Driver 0x1FB0" is a mislabel — 0x1FB0 is the interactive "Ready" main loop (it prints Ready and stores itself as the restart vector); the driver-registration machinery it participates in concerns device-table presence, not data transfer. Likewise "0x2ADF RS-232C receive stub" actually displays character 0x0C (CLS) on the current output device. The real serial driver is the 0x8314–0x86C2 block documented here.

Documentation fix needed in MLLOADER.md: it attributes overruns to "the 64-char UART buffer". The buffer is 256 bytes; the manual's figure of 64 is the remaining headroom when XOFF fires (256 − 192). The overrun explanation (slow per-byte BASIC parsing without XON/XOFF back-pressure) stands.

Emulator gap: both this emulator and the Delphi reference model only the byte stream + host-side XON/XOFF. Gate-array register 0x0006's CTS/DSR/DCD bits are not emulated (register 6 is used only for the cassette carrier bit), so CS=C/DS=D/CD=C opens that would work on real hardware will hang or NR-error differently in emulation. Anyone building a physical interface should test handshake modes on real hardware.

10. Practical recommendations for a reliable link

  • Prefer XON/XOFF (Busy=B, the default). It is honoured in both directions with generous thresholds and is the only flow control the receive path can initiate.
  • Text/hex payloads only when Busy=B — 0x11/0x13 are consumed by the ISR. Hex-encode binaries (as MLLOADER does) or use Busy=N with sender-side pacing.
  • Hardware option: wire PC RTS→Casio CTS and open with CS=C to let the PC throttle the Casio's transmitter. Do not rely on the Casio's RTS/DTR for flow control — they are static.
  • The PC side must honour XOFF within 64 characters (the post-XOFF headroom). At 4800 baud that is ≈150 ms — trivial for hardware UART FIFOs, but beware large OS-level write buffers that keep draining after the application pauses.
  • 4800 baud (6) is safe with flow control on; the manual's advice to stay ≤2400 applies to unthrottled links.
  • No inter-character delay is needed on receive from the Casio — its ISR keeps up at line rate; conversely when sending to the Casio during LOAD, either honour XOFF or budget for tokenization stalls at line ends.
