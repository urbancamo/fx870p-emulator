# FX-870P BASIC Compiler

Compiles Casio JIS Standard BASIC programs into HD61700 machine code for the FX-870P/VX-4.

## Quick Start

```bash
npx tsx tools/compiler/compile.ts program.bas
```

This reads `program.bas` and produces four output files in `build/compiler/`:

| File | Description |
|------|-------------|
| `build/compiler/program.bin` | Raw HD61700 binary |
| `build/compiler/program.hex` | CR-delimited ASCII-hex payload, ready to send over COM0 |
| `build/compiler/program.lst` | 132-column assembly listing with BASIC source annotations |
| `build/compiler/program.sym` | Symbol table (JSON) |

You can also use the npm script shorthand:

```bash
npm run compile -- program.bas
```

The `build/` directory is gitignored.

## Loading a Compiled Program

The loader is generic and lives once in the BASIC program library, not regenerated per
compile — `program.hex` works with whichever copy of `MLLOADER.BAS` is already on the
calculator.

1. **Once per session:** open the library (**LIB**), load `EXTCLR.BAS`, `RUN` it, then type
   `MODE110(&H18F5),1520` when prompted. This reserves the `&H1CD0` machine-code area against
   BASIC's own memory use — **required**, see below for why.
2. Load `MLLOADER.BAS` from the library into a program slot, `RUN` it. LCD shows
   `ML loader - send .hex now`.
3. In the COM0 panel, click **LOAD** and pick the compiler's `program.hex` output.
4. One **BEEP** on success — the compiled program runs automatically via `MODE110`. Three
   **BEEP**s means a checksum mismatch (transfer error); `No ML area!` means step 1 was
   skipped or reserved too little space for this program's size.

See `public/basic/emulator/MLLOADER.md` and `public/basic/emulator/EXTCLR.md` for the full
protocol and mechanism details.

## Output Files

### Binary (`.bin`)

Raw machine code bytes, ORG'd to `&H1CD0` (Bank1 RAM, the standard FX-870P/VX-4 ML area — see "Memory Layout" below). Used directly by the headless debugger (`tools/emu-debugger/`) and by `assemble()`/tests; on real hardware or the browser emulator, send the `.hex` payload to `MLLOADER.BAS` instead — see "Loading a Compiled Program" above.

### Listing (`.lst`)

132-column fixed-width assembly listing designed for monospaced display or printing. Includes:

- Page headers with source filename, date, and total size
- Hex address, machine code bytes, labels, assembly mnemonics, and comments per line
- BASIC source line annotations (`=== BASIC Line 10: PRINT "Hello" ===`) above each generated block
- Symbol table at the end (alphabetical, 4-column layout)
- Size summary showing code, data, variable, and total byte counts

Example:

```
HD61700 Cross Assembler - FX-870P BASIC Compiler                                                                              Page 1
Source: hello.bas  Date: 2026-08-15 06:49  Size: 144 bytes

Addr  Hex Code         Label        Assembly                         Comment
----- ---------------- ------------ -------------------------------- ---------------------------------------------------------------
                                                                     prologue: disable interrupts (see MODE110, rom1a.src:5306)
1CD0  57 20 00                      pst ie,&H00                      ; IE=0: bank-switch pipeline is not interrupt-safe
                                                                     prologue: force OUTDV=0 (LCD)
1CD3  D1 02 39 17                   ldw $2,&H1739                    ; OUTDV addr
1CD7  96 02                         pre ix,$2
1CD9  42 00 00                      ld $0,&H00                       ; LCD device code
1CDC  64 00 00                      std $0,(ix+&H00)                 ; write OUTDV
                                                                     ; === BASIC Line 10: 10 CLS ===
1CDF  D1 02 DF 2A                   ldw $2,&H2ADF                    ; CLS
1CE3  77 36 1D                      cal ROM_CALL
```

Addresses start at `&H1CD0` (see "Memory Layout" below), not `&H0000` — every compiled program is `ORG`'d there.

### Symbol Table (`.sym`)

JSON array of all labels with their resolved (absolute, `&H1CD0`-based) addresses and types:

```json
[
  { "name": "L10", "address": 7388, "type": "code" },
  { "name": "L20", "address": 7395, "type": "code" },
  { "name": "STR_001", "address": 7486, "type": "code" }
]
```

### Hex Payload (`.hex`)

ASCII text, CR-delimited, one field per line — safe for any serial link (no binary escape
hazards) and lets `MLLOADER.BAS` read a fixed-width field at a time via `INPUT$`:

```
[line]  4 hex chars: 16-bit payload size, big-endian
[line]  size × (2 hex chars): binary payload, one byte per line
[line]  2 hex chars: 8-bit additive checksum over payload bytes
```

Generated by `generateHexPayload()` in `loader.ts`. Send it to a running `MLLOADER.BAS` over
COM0 — see "Loading a Compiled Program" above, and `public/basic/emulator/MLLOADER.md` for
the full protocol.

## Pipeline

```
BASIC source
    |
    v
  Lexer (lexer.ts)         -- tokenizes keywords, operators, literals
    |
    v
  Parser (parser.ts)       -- recursive descent with Pratt precedence climbing
    |
    v
  AST (ast.ts types)       -- 33 statement types, 9 expression types
    |
    v
  Code Generator (codegen.ts)  -- emits HD61700 assembly calling ROM routines
    |
    v
  Assembly text (asm-types.ts) -- annotated AsmLine[] with BASIC source refs
    |
    v
  Assembler (assembler.ts)     -- two-pass: label resolution + binary emission
    |                           -- uses opcodes.ts for instruction encoding
    v
  Binary + Hex payload + Listing
```

## How It Works

The compiler does **not** reimplement the BASIC runtime. Instead, generated code calls into the FX-870P's ROM for all high-level operations: PRINT, INPUT, floating-point arithmetic, string handling, etc. This follows the same pattern used by CosmicV4 (a machine language game for the VX-4).

Numeric values (constants, variables, and all arithmetic results) use the ROM's own 9-byte BCD floating-point format — see `bcd.ts` for the encoding (13 significant digits, biased exponent, sign folded into the exponent's hundreds digit) and the design spec at
`docs/superpowers/specs/2026-08-12-compiler-bcd-arithmetic-design.md`. `+`, `-`, `*`, `/`, `MOD`, and all six comparison operators are implemented by calling the ROM's real floating-point routines — no arithmetic is reimplemented in the compiler itself.

Every compiled program's first instruction disables interrupts (`PST IE,&H00`) for the program's whole run, matching what the ROM itself does when BASIC launches machine code via `MODE110`. This isn't an optimisation — every ROM call relies on a one-instruction bank-switch pipeline delay that an interrupt landing at the wrong moment can corrupt (see the comment in `codegen.ts`'s `generate()` for the full mechanism). `IE` is deliberately not restored at the end; `MODE110`'s own return path does that.

Two ROM call wrappers exist, both emitted at the end of every compiled program:

```asm
ROM_CALL:     LDW  $0,&H5323      ; BIOS2 return context
              PHSW $1              ; push return address
              PST  UA,&H54        ; bank switch to Bank0
              JP   $2              ; jump to ROM routine

ROM_CALL_FP:  LDW  $28,&H5323     ; BIOS2 return context (FP-safe: avoids $0-$8)
              PHSW $29             ; push return address
              PST  UA,&H54        ; bank switch to Bank0
              JP   $19             ; jump to ROM routine
```

Most ROM calls (PRINT, CLS, BEEP, etc.) go through `ROM_CALL`: load the routine's address into `$2` and jump to it. Calls that carry a floating-point right-hand operand (arithmetic, comparisons, MOD) go through `ROM_CALL_FP` instead — `ROM_CALL`'s own preamble would clobber registers `$0-$3`, which is exactly where the ROM's FP routines expect that operand to be staged (left operand in `$10-$18`, right operand in `$0-$8`).

## Memory Layout

Compiled programs are always `ORG`'d to `&H1CD0` (see `codegen.ts`) — the standard
FX-870P/VX-4 ML area, matching CosmicV4 and `MLLOADER.BAS`'s fixed load target:

```
0x1CD0  Compiled code (instructions)
        ROM call wrappers
        String literals (DB directives)
        Variable table (9 bytes per numeric, 256 per string)
        Array storage (allocated by DIM)
0x1CD0 + 4095  End of default 4KB budget (WARN_THRESHOLD in compile.ts)
```

The compiler warns if output exceeds 4KB. **This area is not reserved by default** — see the
next section. Plain `CLEAR n,m` does not reserve it either; that command only resizes the
variable/work areas within BASIC's existing (unreserved) bounds, it doesn't carve out
protected space above them. Reserving `&H1CD0` requires the machine-code-level mechanism in
`EXTCLR.BAS`.

## Why EXTCLR.BAS Is Required

`MLLOADER.BAS` will silently corrupt the program it just loaded if `EXTCLR.BAS` hasn't been
run first. This was discovered by capturing live emulator state mid-transfer and loading it
into the headless debugger for byte-level inspection (`tools/emu-debugger/`) — worth knowing
if you hit unexplained garbled output after a successful (checksum-passing!) load.

**The mechanism:** the FX-870P/VX-4 ROM hard-codes the string-operation stack pointer (`US`)
to `&H1CD0` — see `reference/ROM Disassembly/fx870_r1/rom1a.src` at `&H1F64`, `&H66BA`, and
other call sites. This isn't just a one-time boot default: the ROM re-arms `US=&H1CD0` on
essentially *every* string operation, including a transient one whose result is never stored
in a variable.

`INPUT$(1,#1)` — the only primitive `MLLOADER.BAS` can use to read bytes off COM0 — is itself
a string-returning operation. Even written as `A=ASC(INPUT$(1,#1))`, with the string never
named or persisted, the ROM still writes the returned character through `US` at `&H1CD0` as
part of constructing that return value. Because `US` is a fixed address that doesn't track the
receive loop's counter, *every* `INPUT$` call across the whole loop stomps `&H1CD0` — not just
the one for the program's first byte. The loader's own `POKE I,P` for iteration 0 briefly
restores the correct byte there, but every later iteration's `INPUT$` calls overwrite it
again, and nothing pokes it back a second time. The final state of `&H1CD0` ends up being
whatever the very *last* `INPUT$` call in the whole transfer read — deterministically, the
checksum line's trailing CR (`&H0D`) — regardless of what was actually POKEd during the loop,
and regardless of whether the checksum comparison passes (it does: the checksum is computed
from the values POKEd during the loop, before this later overwrite happens). A second,
similarly fixed ROM address corrupts one further byte the same way.

There is no way to avoid this from BASIC alone — `INPUT$`, `INPUT#`, and `LINE INPUT#` are all
string-typed at the ROM level, so any loader that reads serial data character-by-character
will hit it. `EXTCLR.BAS` fixes it by moving `US` (and the UART's own receive-staging buffer)
below `&H1CD0` entirely, via a machine-code stub ported from CosmicV4's proven `clr.b` — see
`public/basic/emulator/EXTCLR.md` for the full mechanism and `MLLOADER.md` for the safety
check `MLLOADER.BAS` now runs before touching any payload byte.

## Known Limitations

BCD constants and arithmetic — `+`, `-`, `*`, `/`, `MOD`, and all six comparisons, plus `DATA` values and `IF`/`WHILE`/`FOR` conditions — are fully implemented and empirically verified against the real ROM (see `bcd.ts`, `tools/emu-debugger/tests/arithmetic-bcd.test.ts`, and `public/basic/emulator/PRIMES.BAS`, verified end-to-end in `tools/emu-debugger/tests/primes.test.ts` to correctly find the 100th prime). Remaining known gaps:

- **String variable assignment is a no-op**: `A$="hello"` (or `A$=B$`) emits no instructions at all — `emitVariableStore` only leaves a `TODO: string copy` comment, since a real assignment needs the ROM's `strcpy`, not yet wired up. No error, no crash — the destination variable's storage is simply left unchanged. String *literals* used directly (e.g. `PRINT "hello"`) are unaffected; only assignment into a string variable is broken.
- **Unary minus is broken**: `-X` XORs a mantissa bit instead of setting the BCD sign (which lives in a different byte — see `bcd.ts`'s `SIGN_OFFSET`). `A=-5` silently produces a wrong positive value, not `-5`. `0-X` (binary subtraction) is unaffected and works correctly.
- **`DEF FN` falls through into its own function body, and `FN` calls emit nothing**: `emitDefFn` emits the function body inline with no jump around it, so a `DEF FN` statement reached in normal control flow *executes* the body and then returns out of the enclosing scope — every statement after the `DEF FN` line is silently skipped. This is worse than a feature that simply doesn't work: the program appears to end early rather than to misbehave at the point of use. Separately, `emitExpression`'s `'fn-call'` case emits no code at all, so an `FN` call leaves whatever happened to be in the accumulator. There is **no workaround** — unlike unary minus, which has `0-X`. Avoid `DEF FN`/`FN` entirely in compiled programs; inline the expression, or use a `GOSUB` with a shared variable, instead.
- **`INPUT` doesn't work from compiled code**: its ROM address is the BASIC interpreter's own `INPUT` *command* handler, which parses source text and isn't callable from machine code — the same class of bug `PRINT` had until it was fixed to use the ROM's internal numeric-formatting routines instead. Not yet fixed for `INPUT`; see the comment on `ROM.INPUT` in `codegen.ts`.
- **`FOR` loops always execute their body at least once**, even when the initial value already fails the end condition (e.g. `FOR I=5 TO 1` should run zero times). The loop-continuation test only runs after the first pass; there's no upfront guard.
- **Integer division (`\`)** isn't wired up — only `MOD` is, which happens to need the same underlying ROM entry point's setup.
- **ROM addresses**: Many builtin function addresses (SIN, COS, TAN, SQR, INT, etc.) are placeholders (`&H0000`). These need to be mapped from the ROM annotations in `reference/fx870p-rom-annotations.md`.
- **Addressing modes**: Some complex programs may hit remaining edge cases where the code generator emits instruction forms that the assembler can't encode.
- **No optimisation**: The compiler emits straightforward code with no peephole optimisation or register allocation beyond the fixed convention.
